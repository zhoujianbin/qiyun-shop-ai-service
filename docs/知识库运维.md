# 知识库运维说明

> 适用：二期（企业知识库平台）。一期（电商底座）运维见 `README.md` 与 `docs/README.md`。

## 1 迁移

### 1.1 三条不变式

1. `db/schema.sql` 是**全量真源**：空库一步建成 55 张表（shared 14 / commerce 32 / knowledge 9）。
2. `db/migrations/00XX_*.sql` 是**增量**：只用于把"已在跑的一期库"升级到二期。
3. `app/models/generated.py` 是**生成物**：改完 DDL 必须重跑 `scripts/gen_models.py`，不要手改。

三者必须一致。校验命令：

```bash
python scripts/gen_models.py && git diff --exit-code db/schema.sql docs/schema.sql app/models/generated.py
```

### 1.2 空库流程（新建环境）

```bash
python scripts/create_db.py --db qiyun_shop_p2 --reset --force   # 建库 + 应用 schema.sql
python scripts/apply_migrations.py --db qiyun_shop_p2            # 记录已执行迁移（空库上等价于幂等重放）
python scripts/seed.py --orders 60                               # 基础数据（含 12 个 knowledge:* 权限码与 4 个角色）
```

预期输出：`schema 应用完成，表数量：55`；`apply_migrations` 结束打印 `base_tables=55`。

> 顺序不可颠倒：`apply_migrations` 只在"库里已有租户"时才补权限与角色；空库上的权限种子由 `seed.py`（`scripts/bootstrap.py`）负责，避免唯一键冲突。

### 1.3 升级流程（已有数据的环境）

```bash
python scripts/apply_migrations.py --dry-run        # 先看将执行哪些文件
python scripts/apply_migrations.py                  # 真正执行（作用于 DATABASE_URL 指向的库）
```

行为：

| 情况 | 处理 |
|---|---|
| 未执行过 | 按文件名顺序执行，单文件一个事务 |
| 已执行且 checksum 一致 | 跳过（`skipped`） |
| 已执行但 checksum 不一致 | **报错退出**（迁移文件被改动过，需要人工确认） |
| 执行失败 | 立即停止，该文件不记录，退出码 1 |

执行记录表 `shared.schema_migration`：`version`、`file_name`、`checksum`、`applied_at`、`applied_by`、`duration_ms`、`success`。

### 1.4 升级后自检

```sql
-- 表数
select count(*) from information_schema.tables
 where table_schema in ('shared','commerce','knowledge') and table_type = 'BASE TABLE';   -- 期望 55

-- 向量维度
select format_type(atttypid, atttypmod) from pg_attribute
 where attrelid = 'knowledge.chunk'::regclass and attname = 'embedding';                  -- 期望 vector(512)

-- 权限码
select count(*) from shared.app_permission where module = 'knowledge';                    -- 期望 12

-- 审计员不得读取知识库正文
select count(*) from shared.app_role_permission rp
  join shared.app_role r on r.id = rp.role_id
  join shared.app_permission p on p.id = rp.permission_id
 where r.code = 'AUDITOR' and p.code like 'knowledge:%';                                  -- 期望 0
```

### 1.5 回滚

| 层面 | 做法 |
|---|---|
| 代码 | 切回 `main`（一期快照） |
| 本地库 | `python scripts/create_db.py --db <库名> --reset --force` 重建（开发环境无生产数据） |
| 已升级的数据环境 | 按 `db/migrations/*.sql` 文件头部的"回滚"注释倒序执行，再删除 `shared.schema_migration` 对应行 |
| 向量维度回退 | 必须**先清空 `knowledge.chunk` 并重建 HNSW**，再执行 `ALTER COLUMN embedding TYPE vector(1024)`；回退后所有向量都要重算 |

> 迁移只做加法（加表、加列、加约束、加索引、收窄授权），不改一期既有列。`knowledge.document.status` 的 CHECK 保持一期取值，待生效状态只写在 `knowledge.document_version.status`。

## 2 向量模型

### 2.1 模型与维度

| 项 | 值 |
|---|---|
| 模型 | `BAAI/bge-small-zh-v1.5` |
| 维度 | **512**（与 `knowledge.chunk.embedding vector(512)` 绑定） |
| 归一化 | L2（cosine 距离等价于内积） |
| 入库侧 | 原文，**不加**指令前缀 |
| 查询侧 | 前缀「为这个句子生成表示以用于检索相关文章：」 |

### 2.2 获取方式

**默认（联网）**：首次调用时自动下载到 `HF_HOME`，默认 `./var/models`（已被 `.gitignore` 忽略）。

```bash
python -c "from app.integrations.embedding import BgeEmbedder; BgeEmbedder().encode(['预热'])"
ls var/models            # 应出现 hub/ 与模型权重
```

**离线（推荐用于生产/无外网环境）**：先在能联网的机器上下载模型目录，拷到目标机，再配置路径。

```bash
# 可联网的机器
python -c "from sentence_transformers import SentenceTransformer; SentenceTransformer('BAAI/bge-small-zh-v1.5').save('/tmp/bge-small-zh-v1.5')"
# 目标机 .env
EMBEDDING_MODEL_PATH=/opt/models/bge-small-zh-v1.5
```

指定 `EMBEDDING_MODEL_PATH` 后**不会联网**；路径不存在会立刻报错（不等到推理时才失败）。

### 2.3 测试环境不加载模型

`APP_ENV=test` 时 `EMBEDDING_PROVIDER=auto` 解析为**确定性 fake**（同文本→同向量、512 维、归一化），因此 `python -m pytest -q` 不会下载或加载模型。真实模型只有 1 条冒烟测试：

```bash
python -m pytest -m slow -q
```

### 2.4 更换模型的影响面

换模型必须**同时**做四件事，缺一不可：

1. 改 `EMBEDDING_MODEL_NAME`/`EMBEDDING_MODEL_PATH` 与 `EMBEDDING_DIM`；
2. 改 `knowledge.chunk.embedding` 的维度（新迁移文件），并**先清空 chunk 再重建 HNSW**；
3. 重跑 `scripts/reindex_embeddings.py` 重算**全部**向量（维度变了旧向量全部作废）；
4. 重跑检索回归，确认阈值 `0.35` 仍然适用（不同模型的相似度分布不同）。

```sql
-- 维度不符会直接拒绝加载模型，可用这条确认当前库的维度
select format_type(atttypid, atttypmod) from pg_attribute
 where attrelid = 'knowledge.chunk'::regclass and attname = 'embedding';
```

## 3 导入

### 3.1 支持与限制

| 项 | 规则 |
|---|---|
| 格式 | `.md`、`.txt`、`.docx`；规则 YAML 走独立通道（见 §3.4） |
| 单文件 | ≤ 20MB（`MAX_UPLOAD_MB`），空文件、扩展名与内容不符一律 422 |
| 批量 | 一次请求多文件（multipart 同名 `files` 字段）；158 篇全量约 650KB |
| front matter | 必填 7 项：`document_id`、`title`、`category`、`version`、`effective_date`、`owner`、`status` |
| 去重 | 按文件 sha256：同一文档的同一内容重复导入 → 计入 `skipped`，不产生新版本 |
| 失败隔离 | 单文件解析失败只进错误清单，不阻塞同批其他文件 |
| 幂等 | 同 `Idempotency-Key` 复用同一任务（multipart 每次边界不同，幂等由 `knowledge.import_job` 保证） |

### 3.2 一次导入全量素材

```bash
# 打包后上传（服务端一次请求多文件）
curl -X POST http://127.0.0.1:8000/api/v1/knowledge/import/jobs \
  -H "Authorization: Bearer $TOKEN" -H "Idempotency-Key: $(uuidgen)" \
  -F "files=@knowledge_raw/00_企业基础/README.md" \
  -F "files=@knowledge_raw/01_产品知识/README.md"

# 查询任务结果
curl -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8000/api/v1/knowledge/import/jobs/1
```

任务结果五字段：`total` / `succeeded` / `failed` / `skipped` / `errors`。

### 3.3 导入后必须做的一步

切片先以 `PENDING` 落库，**检索只使用 `READY`**，所以导入后要跑一次向量化：

```bash
python scripts/knowledge_worker.py --once           # 跑一轮补齐
python scripts/knowledge_worker.py --interval 30    # 生产常驻
python scripts/knowledge_worker.py --retry-failed   # 失败切片放回队列
```

实测（158 篇 / 395 片）：一轮 `--once` 约 7 批、10 秒内完成（CPU）。

### 3.4 规则 YAML

只接受三类形态，其余形态返回 400 并说明"该形态不纳管"：

| 文件 | 条数 | `source_kind` |
|---|---|---|
| `policy_rules.yaml` | 9 | `policy` |
| `product_warranty.yaml` | 7 | `warranty` |
| `escalation_matrix.yaml` | 8 | `escalation` |

### 3.5 后台改稿：保存 → 提交审核 → 发布

运营在后台改一段话不必重新准备文件：

1. 编辑器选中文档 → 自动载入当前生效版本内容；
2. 修改后点「保存为新版本」→ 调 `POST /knowledge/documents/{document_pk}/versions`，生成**草稿**版本（版本号 = 当前最大 +1，`source_kind=MANUAL`），内容重新切片并置 `PENDING`；
3. 跑一次 `python scripts/knowledge_worker.py --once` 补齐向量；
4. 详情页「提交审核」→ 审核通过后「发布」（发布门禁与导入版本完全相同）；
5. 发布后旧版本自动 ARCHIVED，同一文档始终只有一个 ACTIVE。

> 保存不会改动任何已有版本；回滚仍走 `POST /versions/{id}/rollback`。

### 3.6 重算与排障

```bash
python scripts/reindex_embeddings.py                 # 只补 PENDING / FAILED
python scripts/reindex_embeddings.py --force          # 全部重算
python scripts/reindex_embeddings.py --batch 200 --start-id 5000   # 断点续跑
```

常见症状：

| 症状 | 排查 |
|---|---|
| 检索结果为空 | 是否有 `READY` 切片：`select embedding_status, count(*) from knowledge.chunk group by 1;` |
| 版本发布被拒"切片为空" | 该版本 `knowledge.chunk` 是否 0 行（内容过短或解析失败） |
| 导入 `failed` 但原因不明 | 看任务的 `errors`：`file` + `reason` + `line` |
| 向量维度报错 | 见 §2.4 换模型的四步 |

## 4 结构化规则

### 4.1 六键条件契约

`condition` 只允许 6 个语义键：`product_line`、`issue_type`、`order_state`、`identity_level`、`time_window`、`component`；值可以是标量或标量数组（数组 = 任一命中）。其他键一律 422。

`condition` 放"何时适用"，`action` 放"结论与参数"，`forbid` 放"禁止项"。

### 4.2 冲突判定

同一 `conflict_group` 内两条生效规则：

| 情形 | 级别 | 处理 |
|---|---|---|
| 条件相交 + 结论互斥（`ALLOW_*` vs `DENY_*` 等） | `BLOCK` | **阻止发布**，需在 `PATCH /knowledge/rule-conflicts/{id}` 标记 RESOLVED |
| 条件相交 + 同一结论但参数不同 | `WARN` | 提示，不阻止 |
| 条件不相交 | — | 不构成冲突 |

过期规则（`effective_until` 早于当前）**不参与**冲突检测。

### 4.3 25 条映射表

完整映射见 `openspec/changes/phase2-knowledge-platform/design.md` 决策 4：政策 9 + 保修 7 + 升级 8 = 24 条已确认入库；耗材条款（无 `rule_id` 的 `consumables` 块）为待定第 25 条。

### 4.4 导入与排障

```bash
# 一次导入三类 YAML
curl -X POST http://127.0.0.1:8000/api/v1/knowledge/rules/import \
  -H "Authorization: Bearer $TOKEN" \
  -F "files=@knowledge_raw/13_结构化规则/policy_rules.yaml" \
  -F "files=@knowledge_raw/13_结构化规则/product_warranty.yaml" \
  -F "files=@knowledge_raw/13_结构化规则/escalation_matrix.yaml"

# 重算冲突
curl -X POST http://127.0.0.1:8000/api/v1/knowledge/rules/check-conflicts -H "Authorization: Bearer $TOKEN"
```

| 症状 | 排查 |
|---|---|
| 导入返回 400 `RULE_FORM_NOT_MANAGED` | 该 YAML 形态不在纳管范围（只接受 policy / warranty / escalation） |
| 发布被"阻断级规则冲突"拒绝 | `GET /knowledge/rule-conflicts?status=OPEN`，解决后重试 |
| 规则建不进去 | 条件是否用了六键之外的键；`rule_id` 是否重复 |

## 5 检索服务调用约定（供三期直接 import）

三期在同一进程内直接调用，**不走 HTTP**；本期不提供独立的对外检索服务身份。

```python
from app.services.knowledge_retrieval import search

result = search(
    db,
    "门锁没电了怎么办",
    filters={"category": "产品知识", "product_scope": "QL-L3P"},  # 都可省略
    top_k=10,
    actor={"id": 1, "party": "STAFF", "channel_ids": None},        # None = 全渠道
    identity_level="public",                                       # public / customer / agent
)
```

返回结构：

```python
{
  "hits": [{
      "source_type": "chunk",          # 恒为 chunk；结构化规则不参与检索
      "chunk_id": 123,
      "document_id": "KB-RULE-NAV",
      "document_pk": 7,
      "version": 1,
      "chunk_ord": 0,
      "title_path": "产品知识 / 智能门锁 / 电池续航",
      "line_start": 12, "line_end": 18,
      "snippet": "……"                  # 200 字以内，仅用于展示
  }],
  "debug": {
      "vector_score": {"123": 0.62},   # chunk_id -> 分数
      "text_score": {"123": 0.41},
      "fused_score": {"123": 0.032},
      "latency_ms": 24,
      "candidates": 12
  }
}
```

**约定**：

- `hits` 是稳定契约，**不含分数**；三期生成引用只用 `hits`。
- `debug` 仅供调试与验收，**三期不得依赖**（字段可能变）。
- 过滤条件：只查生效版本、未过期、向量就绪、身份等级可见、租户与渠道交集。
- 渠道可见范围由服务端按当前身份推导，客户端传的是交集，不是授权。

## 7 升级规则别名表（三期）

escalation 规则的 triggers 是英文标识符，用户提问是中文，护栏靠别名表桥接。

| 项 | 说明 |
|---|---|
| 真源 | knowledge_raw/13_结构化规则/escalation_aliases.yaml（业务可直接编辑，改完不需要改代码） |
| 回退 | 文件缺失或损坏时使用 app/services/assistant_graph.py 里的 BUILTIN_ALIASES，并打 WARN 日志 |
| 门禁 | python -m pytest -q tests/test_assistant_guard_alias.py；带禁止项的规则若某触发词没有中文别名，测试失败并打印 rule_id:trigger |
| 命中逻辑 | guard_hints() 用「trigger 原文 或 任一中方别名 出现在问题里」判定命中，命中即取该规则 forbid 追加安全提示 |

**新增一条升级规则时**：先在 escalation_matrix.yaml 写规则，再到 escalation_aliases.yaml 给它补中文别名，最后跑上面的门禁命令。

## 8 本体维护（四期）

| 项 | 说明 |
|---|---|
| 真源 | 实体/关系/别名存库（`ontology` schema）；**导入来源**是 `knowledge_raw/13_结构化规则/` 与 `01_产品知识/*/故障诊断.md` |
| 一键种子 | `python scripts/ontology_seed.py --auto-approve --with-backfill --with-scope-backfill`（幂等，可重复跑） |
| 只有 APPROVED 生效 | 实体/关系/别名均为 `DRAFT/APPROVED/DEPRECATED`；检索、归一、图遍历只认 `APPROVED` |
| AI 审核结论 | `app/services/ontology_review.py` 里的 REJECT/WARN 两张表就是审核结果，改完重跑种子脚本即生效；留痕见 `docs/四期/03_本体抽取与审核记录.md` |
| 换版重挂 | 文档发新版后执行 `POST /api/v1/knowledge/ontology/chunks/relink`，按 `document_id+version+chunk_ord` 重挂，**不重跑实体抽取** |
| 产品范围回填 | `--with-scope-backfill` 只把"切片唯一归属某产品"的文档补上 `product_scope`；已有值不动 |
| 检索集成 | 归一命中实体 → 只有该产品范围在二期确有 ACTIVE 文档时才加过滤；过滤后 0 命中自动回退并留 `filter_fallback` 痕迹 |
| 门禁 | `python -m pytest -q tests/test_ontology*.py tests/test_assistant_tool_branch.py` |

**新增一条本体关系时**：优先在 `13_结构化规则` 里加数据并重跑导入；只有文档里抽不出来的才走后台接口手工建，建成 `DRAFT` 并审核通过。
