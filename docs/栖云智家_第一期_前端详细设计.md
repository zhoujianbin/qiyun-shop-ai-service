# 栖云智家科技有限公司 第一期 企业电商基础平台 前端详细设计

> 文档编号：QY-EC-P1-FE-DD｜版本：V1.0｜编制：前端架构组｜评审：产品、后端、测试、运维
> 适用范围：栖云智家科技有限公司第一期企业电商基础平台的全部前端工程（C 端商城 + B 端运营后台）。
> 本文只描述第一期范围；知识库、RAG 智能客服、本体与工具调用仅在“预留扩展点”一章出现。

## 0 事实基线与范围边界

### 0.1 企业与业务事实

| 项 | 事实 | 对前端的影响 |
|---|---|---|
| 企业 | 栖云智家科技有限公司 | 品牌名、页脚、版权、发票抬头固定为该主体 |
| 产品线 | 智能门锁、家用摄像头、清洁机器人、智能灯具、家庭网关、配件耗材 | 商品类目树与筛选维度按产品线预置；配件耗材必须与主商品建立适配关系展示 |
| 服务 | 云服务、上门安装与维修 | 商品详情需展示安装条件、服务范围、保修摘要；订单可携带安装/服务属性 |
| 渠道 | 官方商城、电商官方旗舰店、授权零售门店 | 库存与订单必须按渠道隔离；后台所有列表默认带渠道范围过滤 |
| 客户 | C 端用户（自然人） | C 端登录态、地址簿、发票抬头、售后凭证均归属本人 |

### 0.2 一期范围与边界

| 类别 | 一期纳入 | 一期不纳入 |
|---|---|---|
| 业务域 | 商品、客户、库存、订单、支付、履约、售后、发票、组织权限、审计 | 智能客服、知识库、RAG、本体、工具调用、自动退款、设备远程控制 |
| 交互能力 | 浏览、加购、下单、支付、发货、物流、售后申请、退款审核 | 对话式客服、AI 草稿、语义检索、自动工单分派 |
| 数据能力 | 单库多 schema 的业务读写与审计查询 | 向量检索、知识版本治理、实体关系推理 |

### 0.5 状态机基线

| 状态机 | 取值 |
|---|---|
| 订单 status | CREATED、PENDING_PAYMENT、PAID、FULFILLING、SHIPPED、COMPLETED、CANCELLED、CLOSED |
| 支付 payment_status | UNPAID、PARTIAL、PAID、REFUNDING、REFUNDED |
| 履约 fulfillment_status | UNSHIPPED、PARTIAL_SHIPPED、SHIPPED、DELIVERED |
| 售后 after_sales_status | NONE、APPLYING、PROCESSING、COMPLETED、REJECTED |

> 前端只做“展示 + 可用动作裁剪”，状态流转的唯一权威在后端。前端不得自行推导非法流转，也不得把状态机枚举写成中文再做反查匹配。

### 0.6 金额、库存、幂等三条硬约束

| 约束 | 后端事实 | 前端强制要求 |
|---|---|---|
| 金额 | numeric(14,2)，币种 CNY，禁止浮点 | 全部金额以 string 承载与展示；运算使用整数分；禁止 Number 直接参与金额加减 |
| 库存 | 可售/锁定/在途/安全库存 + 只追加流水 | 库存调整必须填原因、必须落流水；界面不得出现可编辑的“最终库存值”反推 |
| 幂等 | Idempotency-Key 写入 shared.idempotency_record，业务写接口强制 | 每个写请求在“用户点击一次提交”的粒度生成一个 UUID 并复用重试；不允许在循环中复用同一 key 的多次不同意图 |

## 1 前端选型结论与理由

### 1.1 选型结论总表

| 领域 | 选型 | 版本 | 结论与主要理由 |
|---|---|---|---|
| 视图层 | React | 18 | 生态最成熟、类型友好、Portal/Suspense 能力满足后台与商城；招人与长期维护成本最低 |
| 语言 | TypeScript | 5 | 与 Pydantic/OpenAPI 生成类型天然衔接，可在编译期拦截金额、状态枚举、权限码的误用 |
| 构建 | Vite 6 | 6 | 冷启动快、Rollup 产物可控、支持多入口与静态资源指纹，产物可直接被 FastAPI StaticFiles 挂载 |
| UI 组件 | Ant Design 5 | 5 | 表格/表单/日期/上传等重后台组件齐全，Design Token 体系支持主题与暗色，中文语境默认体验好 |
| 服务端状态 | TanStack Query | v5 | 缓存、失效、重试、并发去重、分页与乐观更新一体化，正好覆盖电商后台的列表与详情场景 |
| 客户端状态 | Zustand | 最新 4.x | API 极小、无 Provider 嵌套、切片式划分清晰，仅承载登录态/权限/渠道/UI 偏好等真正的全局客户端状态 |
| 路由 | React Router | 6 | 嵌套路由 + 数据路由 + loader/错误边界，配合懒加载实现按角色分包 |
| 图表 | ECharts 5 | 5 | 国产图表事实标准，报表工作台折线/柱状/漏斗/地图能力完整，中文坐标与 tooltip 无需额外适配 |
| 契约类型 | openapi-typescript | 最新 7.x | 从 FastAPI 导出的 OpenAPI 3.1 直接生成 types，落库字段严格对齐，避免手写 DTO 漂移 |

### 1.2 React 18 + TypeScript 5

- 选择 React 18 的并发特性（startTransition、useDeferredValue）用于商品筛选与订单列表的高频输入，避免表格重渲染卡顿。
- 组件全部为函数组件 + Hooks，禁止 class 组件；类型 `strict: true`，`noImplicitAny`、`noUncheckedIndexedAccess` 开启。
- 状态枚举、权限码、金额类型统一在 `src/types` 与 `src/constants` 收敛，禁止在页面散落字符串字面量。
- 与 Python 后端的类型对齐通过 openapi-typescript 生成，前端不手写与数据库字段同名的接口模型。

### 1.3 Vite 6 + 产物进 app/static/dist/

- `base` 设为 `/static/dist/`，构建产物带内容哈希，长期缓存；`index.html` 由 FastAPI 模板注入或直接回源。
- 多入口：`index.html`（C 端商城 + B 端后台同一 SPA，按路由分包），后续如需独立后台域可直接增加入口，不影响一期。
- 生产构建关闭 sourcemap 公网暴露，改为上传到对象存储供内部排障；`build.target` 对齐浏览器矩阵（Chrome/Edge 100+、Safari 15.4+）。

### 1.4 Ant Design 5

- 使用 ConfigProvider 统一主题、中文 locale（zh_CN）、日期库 dayjs。
- 表格、表单、上传、抽屉、时间线等重组件直接复用，减少自研成本与无障碍缺陷。
- 仅对 Table/Form 做薄封装（见第 5 章），不重写组件库；业务组件一律通过 Token 而不是内联样式改样式。
- 危险操作统一走 Popconfirm/Modal.confirm 的自研 ConfirmDialog 封装，保证二次确认与影响提示一致。

### 1.5 TanStack Query v5

- 后端返回的一切数据（商品、库存、订单、客户、审计、报表）都归 Query 管理；Zustand 不复制服务端数据。
- 统一 `queryKey` 工厂与失效矩阵（见 6.5、6.6），mutation 成功后精确失效而不是全局 refetch。
- 列表分页统一 `keepPreviousData`（v5 的 placeholderData），翻页不闪空。

### 1.6 Zustand

- 仅管理：登录态与 token、当前员工与权限集合、渠道范围、UI 偏好（侧栏折叠、表格密度、暗色）、全局通知。
- 每个 store 使用 `create` + `persist` 中间件按需落 sessionStorage，敏感 token 不落 localStorage（见 7.2）。

### 1.7 React Router 6

- `createBrowserRouter` + 嵌套路由，`/` 下挂 CustomerShell，`/admin` 下挂 AdminShell。
- 每个一级路由配置 `lazy` 分包；`errorElement` 统一渲染 ErrorState。
- 筛选条件写入 URL query，保证深链、刷新、前进后退可复现。

### 1.8 ECharts 5

- 按需引入（`echarts/core` + 具体 chart/component），禁止整包引入；图表统一封装为 `ChartCard`，内部处理 resize、loading、空数据与可访问文本摘要。

### 1.9 openapi-typescript

- 由后端在 CI 中导出 `contracts/openapi.json`，前端 `pnpm gen:api` 生成 `src/api/generated/schema.d.ts`。
- 生成文件只读，禁止手改；类型不一致时以契约为准并回改后端。
- E2E 同样以该契约为准，Python Playwright 断言响应结构与生成类型一致。

### 1.10 否决 Vue 3 + Element Plus 的对比结论

| 维度 | React 18 + AntD 5（选用） | Vue 3 + Element Plus（否决） | 结论 |
|---|---|---|---|
| 复杂后台表格/表单 | AntD Table/Form 的受控能力与类型推导更成熟 | Element Plus 表单校验与类型推导稍弱 | 选 React |
| 与 OpenAPI 生成类型协作 | openapi-typescript 对 React 生态文档与示例充分 | 需额外评估生成器与 TSX 协作 | 选 React |
| 团队与招聘 | 前端人才池更大 | 可维护性依赖更小的团队 | 选 React |
| 与后端协作 | 同一 TS 契约工具链已被团队验证 | 同样可行但无增量收益 | 选 React |
| 结论 | — | — | **否决 Vue 3 + Element Plus**：在复杂表格、类型推导、契约工具链与人才供给四项上均无优势，切换只会增加迁移与培训成本 |

### 1.11 与 Python 单体仓库的协作方式

| 协作面 | 约定 |
|---|---|
| 仓库结构 | 单体仓库根目录含后端包与 `web/`；前端不单独建库，不引入第二套 CI |
| 契约 | 后端导出 `contracts/openapi.json`，前端生成类型；契约变更走同一 PR |
| 构建 | `pnpm --dir web build` 输出到 `app/static/dist/`；本地开发 `vite dev` 代理 `/api` 到 FastAPI |
| 挂载 | FastAPI 用 `StaticFiles` 挂载 `/static/dist`，SPA 回退到 `index.html`；`/api/v1/**` 优先于静态路由 |
| 鉴权 | 一期采用 Bearer access token（短期、内存）+ refresh token（HttpOnly Cookie），与后端一致 |
| 幂等 | 业务写接口由前端生成 Idempotency-Key 头，后端写 `shared.idempotency_record` |
| E2E | 统一 Python Playwright，放在仓库 `tests/e2e/`，由 FastAPI 启动同一进程与测试数据库；`web/` 内不放置 Playwright 配置 |
| 类型 | 前端生成的 schema 与后端 Pydantic 模型同源，禁止两套 DTO |

### 3.4 懒加载与错误边界

- 一级路由 `lazy(() => import(...))` 分包；`/admin` 与 C 端主包通过 `manualChunks` 拆出 vendor、antd、echarts 三块。
- 每个路由组挂 `errorElement`，渲染 ErrorState 并展示 `request_id`；路由级 `Suspense` fallback 使用 LoadingSkeleton。
- 404 与 403 独立页面；403 展示所需权限码，便于运维定位。

## 4 逐页规格

> 每页统一要求：首屏 skeleton；数据空渲染 EmptyState；失败渲染 ErrorState 并带 request_id；无写权限时整页只读（禁用而非隐藏危险入口，除权限本就不该看到的功能外）；部分失败（如并发场景下的支付/物流分支）用局部 Partial 提示而非整页报错。

### 4.1 商品列表（B 端 `/admin/products`）

**区块**：页头（标题 + 新建商品按钮）→ FilterBar → DataTable → 分页；右侧抽屉为快速预览。

| 字段 | 控件 | 校验 | 说明 |
|---|---|---|---|
| 商品名称/SPU | Input.Search | ≤128 字符 | 支持模糊匹配 |
| 商品编码 | Input | ≤64，字母数字与 `-` | 精确匹配 |
| 产品线 | Select | 枚举：门锁/摄像头/清洁机器人/智能灯具/网关/配件耗材 | 来自后端字典 |
| 类目 | TreeSelect | 必选其一或空 | 支持父子联动 |
| 品牌 | Select | — | — |
| 渠道 | ChannelScopeSelect | 默认当前渠道范围 | 多渠道时多选 |
| 状态 | Select | ON_SALE/OFF_SHELF/DRAFT | 映射 StatusTag |
| 更新时间 | DatePicker.RangePicker | 起 ≤ 止 | 传 ISO8601 |

| 交互 | 规则 |
|---|---|
| 新建 | 需 `shop:product:write`，跳 `/admin/products/new` |
| 批量上下架 | 勾选行后出现；ConfirmDialog 必须展示数量、目标状态、影响渠道 |
| 筛选写入 URL | `?q=&productLine=&status=&page=1&pageSize=20` |
| 排序 | 更新时间/价格/销量，后端排序参数 `sort=` |
| 行点击 | 进入编辑页；操作列含查看、编辑、上下架 |

| 状态 | 表现 |
|---|---|
| loading | 表头保留 + 8 行 skeleton |
| empty | EmptyState 文案“没有符合条件的商品”，含“清空筛选”与“新建商品” |
| error | ErrorState + 重试；保留上次筛选 |
| readonly | 无写权限时隐藏批量操作栏，操作列仅“查看” |
| 埋点 | `product_list_view`、`product_filter_apply`、`product_bulk_status_change` |

### 4.2 商品编辑（B 端 `/admin/products/:productId`、`/admin/products/new`）

**区块**：面包屑 → 分步表单（基本信息 / 规格属性 / 图文详情 / 服务与保修 / 渠道与价格）→ 右侧锚点导航 → 底部固定操作栏。

| 字段 | 控件 | 必填 | 校验规则 |
|---|---|---|---|
| 商品名称 | Input | 是 | 2–128 字符，禁止纯空白 |
| 商品编码 | Input | 是 | 2–64，正则 `^[A-Za-z0-9_-]+$`，全表唯一 |
| 产品线 | Select | 是 | 枚举 |
| 类目 | TreeSelect | 是 | 叶子节点优先 |
| 品牌 | Select | 是 | — |
| 型号 | Input | 是 | ≤64，与产品线组合唯一 |
| 主图 | Uploader | 是 | 1–8 张，JPG/PNG/WebP，≤5MB，建议 1:1 |
| 详情图 | Uploader | 否 | 0–20 张，长图 |
| 规格属性 | 动态键值表 | 按类目 | 键名来自类目模板；数值型走单位校验 |
| 适配配件 | SkuSelector（多选） | 否 | 仅同产品线可选；建立适配关系 |
| 供电/协议/防护等级 | Input/Select | 按类目 | 门锁、摄像头、网关必填 |
| 安装条件与服务范围 | TextArea | 否 | ≤1000 字符；上门服务商品必填 |
| 保修摘要 | TextArea | 是 | ≤500 字符 |
| 渠道与价格 | 渠道行内表 | 是 | 每渠道至少一行；价格见 MoneyInput 规则 |

| 交互 | 规则 |
|---|---|
| 保存草稿 | 不校验完整性，仅记录 |
| 提交上架 | 完整校验；失败定位到首个错误字段并滚动 |
| 离开拦截 | 表单脏时弹 ConfirmDialog“放弃未保存修改” |
| 并发编辑 | 携带 `updated_at` 作为乐观锁；409 提示“已被他人修改”并刷新 |
| 状态 | loading=骨架；readonly=无写权限整页禁用；partial=主档成功但图片上传失败时局部重试 |
| 埋点 | `product_edit_open`、`product_save_success/fail`、`product_publish` |

### 4.3 SKU 与库存调整（B 端 `/admin/skus`、`/admin/inventory`）

**SKU 区块**：SKU 表（编码、规格组合、渠道、成本价、销售价、状态）；行内“库存调整”打开 StockAdjustDialog。

| 字段 | 控件 | 校验规则 |
|---|---|---|
| SKU 编码 | Input | 2–64，唯一，正则同商品编码 |
| 规格组合 | 动态规格选择器 | 组合在商品内唯一 |
| 成本价/销售价 | MoneyInput | 0.00–99999999.99，两位小数，禁止负值 |
| 库存状态 | Select | 由流水推导，前端只读展示 |
| 条码 | Input | ≤64，可空 |

**库存调整对话框 StockAdjustDialog**

| 字段 | 控件 | 校验规则 |
|---|---|---|
| SKU | 只读展示 | 必须已选中 |
| 仓库 | Select | 必选；仅显示有权限仓库 |
| 调整类型 | Radio | 入库 / 出库 / 盘点修正 / 锁定释放 |
| 调整数量 | InputNumber | 正整数；出库与盘点修正不得超过可售数（除强制盘点需管理员） |
| 调整原因 | Select + TextArea | 必选枚举；“其他”时文本必填，≤200 字符 |
| 幂等 | 隐藏 | 打开对话框即生成 Idempotency-Key，重试复用 |

| 交互 | 规则 |
|---|---|
| 提交前预览 | 展示“调整前可售 → 调整后可售”，锁定/在途不变 |
| 成功 | 关闭弹窗、失效库存总览与流水、Toast 展示流水号 |
| 失败 409 | 提示“库存已变化，请刷新后重试”，并自动刷新当前库存 |
| 状态 | 只读角色（如财务）不显示调整按钮；无 `shop:inventory:write` 时整个对话框不可达 |
| 埋点 | `stock_adjust_open`、`stock_adjust_success`、`stock_adjust_conflict` |

| 字段 | 控件 | 校验 |

| 订单状态 | Select | 8 个枚举 |
| 支付状态 | Select | 5 个枚举 |
| 履约状态 | Select | 4 个枚举 |
| 售后状态 | Select | 5 个枚举 |
| 渠道 | ChannelScopeSelect | 默认范围 |
| 下单时间 | RangePicker | 起 ≤ 止，跨度 ≤90 天提示 |
| 金额区间 | 两个 MoneyInput | 起 ≤ 止 |

| 列 | 说明 |
|---|---|
| 订单号 | CopyableText |
| 客户 | 脱敏姓名 + 手机后四位 |
| 金额 | MoneyText，含实付与应付 |
| 状态组 | StatusTag×4（订单/支付/履约/售后），颜色+文字+图标 |
| 渠道/来源 | 渠道标签 |

### 4.5 订单详情（B 端 `/admin/orders/:orderNo`）

**区块**：头部状态条（OrderStatusSteps）→ 左侧主区（商品明细 / 支付信息 / 履约与包裹 / 售后单 / 发票）→ 右侧操作区（可用动作、时间线、客户信息）。

| 动作 | 前置状态 | 权限 | 交互与校验 |
|---|---|---|---|
| 发货 | status ∈ {PAID, FULFILLING}；fulfillment ≠ SHIPPED | `shop:fulfillment:write` | ShipDialog：承运商、运单号、包裹商品、预计到达；运单号正则按承运商校验；支持部分发货 |
| 取消订单 | status ∈ {CREATED, PENDING_PAYMENT}；或 PAID 且未发货需走退款流程 | `shop:order:write` | ConfirmDialog 必须展示“不可逆”、取消原因（枚举+文本）、金额处置 |
| 修改地址 | status ∈ {CREATED, PENDING_PAYMENT, PAID} 且未发货 | `shop:order:write` | AddressForm 复用 C 端地址表单；展示“发货后不可修改”提示 |
| 修改备注 | 任意未完成状态 | `shop:order:write` | ≤200 字符 |
| 发起退款 | payment_status ∈ {PAID, PARTIAL} | `shop:aftersales:review` | 跳转退款审核 |
| 开票 | order 已完成且未开票 | `shop:invoice:write` | 跳转发票页 |

**时间线 OrderTimeline** 事件源：订单创建、支付成功、库存锁定、仓库分配、发货、物流节点、签收、售后发起、退款、关闭。每个节点展示操作者（员工姓名或“系统”）、时间、request_id（可复制）。

| 状态 | 表现 |
|---|---|
| loading | 头部与主区骨架 |

## 6 API 层设计

### 6.1 openapi-typescript 生成类型

| 步骤 | 命令/位置 | 说明 |
|---|---|---|
| 后端导出 | 仓库 `contracts/openapi.json` | 由 FastAPI 在 CI 导出，随 PR 更新 |
| 前端生成 | `pnpm --dir web gen:api` | 执行 `scripts/gen-api.mjs`，调用 openapi-typescript |
| 产物 | `src/api/generated/schema.d.ts` | 只读，禁止手改；由 CI 校验与契约一致 |
| 领域别名 | `src/types/domain.ts` | `type Order = components["schemas"]["Order"]` 等语义别名 |
| 门禁 | CI `openapi-typescript --check` | 契约变更未重新生成时构建失败 |

规则：页面只使用 `endpoints/*.ts` 暴露的领域函数；禁止在页面写 URL；禁止 `as any`（ESLint 禁止）。

### 6.2 统一 fetch 封装（`src/api/client.ts`）

| 能力 | 实现 |
|---|---|
| 基址 | `import.meta.env.VITE_API_BASE` 默认 `/api/v1` |
| 认证 | 自动附加 `Authorization: Bearer <access_token>`（内存态），不写入 URL |
| 刷新 | 401 时单飞刷新 refresh token，刷新成功后重放原请求一次；刷新失败清空登录态并跳登录 |
| 幂等 | 写请求自动附加 `Idempotency-Key`；key 由调用方（用户提交动作）生成，重试复用 |
| request_id | 每个请求生成 `X-Request-Id` 并透传；响应头若返回同名则以后端为准 |
| 渠道 | 若当前页面 channelScoped，自动附加 `X-Channel-Scope` 或查询参数（以契约定义为准） |
| 超时 | 默认 15s；上传 120s；报表导出 60s；均支持 AbortSignal |
| 取消 | 页面卸载、筛选切换、路由跳转时 abort |
| 序列化 | JSON；金额字段始终以字符串传，禁止 `parseFloat` 后再序列化 |
| 响应校验 | 开发环境开启轻量 schema 断言；生产关闭以省体积 |
| 重试 | 仅幂等请求（GET/HEAD）与幂等写（带 Idempotency-Key）按策略重试 |

### 6.3 错误码到 UI 映射（`src/api/errors.ts`）

| HTTP | 错误码/语义 | UI 表现 |
|---|---|---|
| 400 | 参数错误 | 表单顶部 Alert + 字段级 error |
| 401 | 未认证/过期 | 单飞刷新；失败则跳 `/login?redirect=`，Toast“登录已过期” |
| 403 | 权限不足 | 页面级跳 `/admin/403`；按钮级 Toast“无权限，需要 `shop:xxx`” |
| 404 | 资源不存在 | EmptyState 变体“资源不存在或已删除” |
| 409 | 状态冲突/幂等冲突 | 提示“数据已变化，已为你刷新”，自动失效相关 query |
| 422 | 校验失败（Pydantic） | 按 `errors[].loc` 映射到字段级错误 |
| 429 | 限流 | 展示倒计时，禁用提交直到可重试 |
| 5xx | 服务异常 | ErrorState + request_id + 可重试；写操作提示“请勿重复提交，可凭订单号查询” |
| 网络错误 | 断网/超时 | 可重试 ErrorState；写操作提示结果未知，提供查询入口 |

### 6.4 重试策略

| 请求类型 | 重试 | 次数 | 退避 |
|---|---|---|---|
| GET/HEAD（幂等读） | 允许 | 2 | 300ms、900ms + 抖动 |
| 写请求（带 Idempotency-Key） | 仅网络层失败允许 | 1 | 500ms |
| 上传 | 允许分片重试 | 3 | 指数退避 |
| 401 刷新后 | 原请求重放 | 1 | 立即 |
| 4xx（除 401/429） | 不重试 | — | — |

> 业务红线：写操作在响应未知时不盲目重复。重试必须复用同一 Idempotency-Key，并在 UI 上明确“正在确认结果”。

| 退款详情 | `["refunds","detail",refundId]` |
| 售后列表/详情 | `["afterSales","list",filters]` / `["afterSales","detail",ticketId]` |
| 客户列表/详情 | `["customers","list",filters]` / `["customers","detail",customerId]` |
| 员工/角色 | `["staff","list",filters]` / `["roles","list"]` |
| 渠道 | `["channels","list",filters]` |
| 审计 | `["audit","list",filters]` |
| 报表 | `["reports",reportName,params]` |
| 当前用户 | `["me"]` |

约定：key 第一段为资源域，第二段为 list/detail，第三段为对象参数；参数对象键顺序稳定（`useUrlFilters` 统一构造）。

### 6.6 失效策略（`src/api/invalidation.ts`）

| 触发 | 失效范围 |
|---|---|
| 商品保存/上下架 | `["products"]` 全部 list + 该 detail |
| SKU 保存 | `["skus"]` list + `["products","detail"]` |
| 库存调整 | `["inventory"]` 全部 + `["skus"]` list |
| 订单发货 | `["orders","detail",orderNo]` + `["orders","list"]` + `["fulfillment"]` + `["inventory"]` |
| 订单取消/退款 | 该订单 detail + `["orders","list"]` + `["refunds"]` + `["inventory"]` |
| 售后处理 | 该 ticket detail + `["afterSales","list"]` + 关联 `["orders","detail"]` |
| 员工/角色变更 | `["staff"]`、`["roles"]`、`["me"]` |
| 渠道变更 | `["channels"]`、`["me"]` |
| 开票 | `["invoices"]` + 关联订单 detail |

手动失效优先于 `invalidateQueries()` 全局广播；跨页共享资源使用资源前缀失效。

### 6.7 乐观更新边界

| 场景 | 是否乐观 | 说明 |
|---|---|---|
| 购物车改数量 | 是 | 立即更新，失败回滚并 Toast |
| 地址默认/删除 | 是 | 本地列表即时更新 |
| 后台列表页内联编辑（如备注） | 否 | 需服务端确认后再更新 |
| 订单状态类动作（发货、取消、退款） | 否 | 必须等待服务端确认，避免误解为已生效 |
| 库存调整 | 否 | 金额与库存不可乐观 |
| 表单保存 | 否 | 成功后再更新缓存 |

## 7 状态与权限

### 7.1 Zustand store 划分

| store | 状态 | actions | 持久化 |
|---|---|---|---|
| `authStore` | user、roles、accessToken（内存）、expiresAt、登录状态机（idle/loading/authed/expired） | login、logout、refresh、bootstrap | 仅 user 摘要与 expiresAt 落 sessionStorage；token 不落 localStorage |
| `permissionStore` | permissions: Set<string> | setPermissions、has、hasAny | 派生自 user，不单独持久化 |
| `channelScopeStore` | availableChannels、activeChannelIds | setScope、reset | sessionStorage |
| `uiStore` | 侧栏折叠、表格密度、主题（light/dark/system）、语言 | toggleSider、setDensity、setTheme、setLocale | localStorage（非敏感） |
| `noticeStore` | 全局 Toast/通知队列 | push、dismiss | 不持久化 |

约束：服务端资源数据一律在 TanStack Query；两个系统之间通过 `useMe()` 初始注入，不在 store 内 `fetch`。

### 7.2 登录态与刷新 token

| 项 | 方案 |
|---|---|
| access token | 短期 JWT，仅存内存（`authStore`），页面刷新通过 refresh 恢复 |
| refresh token | HttpOnly + Secure + SameSite=Lax Cookie，前端不可读 |
| 刷新时机 | 请求 401 时单飞刷新；也可在 expiresAt 前 60s 预刷新 |
| 单飞 | 并发 401 共用同一个刷新 Promise，避免雪崩 |
| 多标签 | 使用 BroadcastChannel 同步登出；某标签登出后其他标签跳登录 |
| 登出 | 调 `POST /auth/logout` 清 Cookie，清空 query cache 与 store |
| 页面刷新 | `bootstrap()` 调 `GET /auth/me` 恢复权限与渠道范围 |

### 7.3 路由守卫

| 守卫 | 行为 |
|---|---|
| AuthGuard | 未登录跳 `/login?redirect=<当前路径>`；bootstrap 中显示全屏 loading |
| PermissionGuard | 读 `route.meta.permissions`，缺任一权限跳 `/admin/403` |
| ChannelGuard | `channelScoped` 路由在无可用渠道时展示“无渠道授权”空态 |
| CustomerGuard | C 端资源页校验本人；后端 owner 校验为最终权威，前端 403 时展示无权限 |
| 登出清场 | queryClient.clear()、AbortController.abort()、断开后续实时能力（本期无 WS） |

### 7.4 按钮级权限 PermissionGate

```tsx
<PermissionGate permission="shop:inventory:write" mode="disable" fallbackReason="需要库存写权限">
  <Button type="primary">库存调整</Button>
</PermissionGate>
```

| 约定 | 说明 |
|---|---|
| 权限码来源 | `src/types/permissions.ts` 常量，禁止字面量 |
| mode | `hide`（默认）或 `disable`；危险操作建议 disable 并给原因，避免用户困惑 |
| 后端为准 | 前端权限仅用于体验；所有写请求后端必须再校验，403 统一处理 |
| 角色差异 | 例如财务/审计为 `shop:payment:read`、`shop:invoice:read`，写按钮禁用 |

### 7.5 渠道范围过滤

| 规则 | 说明 |
|---|---|
| 数据来源 | 登录 `GET /auth/me` 返回可用渠道；管理员可切换全部或子集 |
| 注入 | 所有 list 请求携带 `channel`/`channelIds` 参数 |
| UI | AdminTopBar 常驻 ChannelScopeSelect，变更即失效当前页 list |
| 越权 | 后端校验渠道归属；前端 403 时提示“当前渠道范围无权限” |
| 默认 | 只配置一个渠道时仍显示但不可切换 |

## 8 表单与校验规则

### 8.1 金额与库存展示规范

| 主题 | 规范 |
|---|---|
| 金额类型 | 全链路 string（表单值、state、URL、payload）；禁止 float 运算 |
| 金额运算 | 需要合计时转整数分，使用 `utils/money.ts` 的 `addMoney/subMoney` |
| 展示格式 | `¥1,234.50`；负数红色并带 `-`；等宽数字 `font-variant-numeric: tabular-nums` |
| 币种 | 一期固定 CNY，界面不提供币种切换 |
| 精度 | 两位小数；输入禁止超过两位，禁止科学计数法 |
| 库存展示 | 可售/锁定/在途/安全库存分列；低于安全库存用警示色 + 图标 |
| 库存编辑 | 只允许通过调整流水改变，不提供直接写最终值 |
| 数量 | 加购/下单数量为整数，1 ≤ n ≤ 可售 |

### 8.2 字段级校验表（与后端规则一致）

| 字段 | 规则 | 前端表现 |
|---|---|---|
| 商品名称 | 2–128 字符 | 长度计数、trim 后校验 |
| 商品/SKU 编码 | 2–64，`^[A-Za-z0-9_-]+$`，唯一 | 实时正则；409 时字段级报“编码已存在” |
| 价格 | 0.00–99999999.99，两位小数 | MoneyInput 限制输入字符 |
| 库存调整数量 | 正整数；出库 ≤ 可售 | 超限立即报错并禁用提交 |
| 调整原因 | 必选；其他时文本 ≤200 | 条件必填 |
| 订单取消原因 | 必选枚举；其他时文本 ≤200 | 条件必填 |
| 运单号 | 按承运商正则；1–64 | 选择承运商后动态规则 |
| 退款金额 | 0.01–可退金额 | 超限报错 |
| 售后描述 | ≤500 字符 | 计数 |
| 上传凭证 | ≤9 张，单文件 ≤10MB，类型白名单 | 上传前校验，失败可重试 |
| 收件人/手机/省市区/详址 | 必填；手机 11 位 | 地址表单一次性校验 |
| 发票抬头 | 个人：姓名；企业：名称+税号（15–20 位） | 切换类型动态校验 |
| 员工登录名 | 4–32，`^[a-z0-9._-]+$`，唯一 | 409 字段级 |
| 密码 | 8–64，含字母与数字 | 强度提示 |

### 8.3 状态机驱动的动作可用性

| 动作 | 可用前置条件 |
|---|---|
| 发货 | status ∈ {PAID, FULFILLING} 且 fulfillment_status ≠ SHIPPED |
| 取消订单 | status ∈ {CREATED, PENDING_PAYMENT} |
| 修改地址 | status ∈ {CREATED, PENDING_PAYMENT, PAID} 且未发货 |
| 退款审核通过 | after_sales_status ∈ {APPLYING, PROCESSING} 且 payment_status ∈ {PAID, PARTIAL} |
| 完成售后 | after_sales_status = PROCESSING |
| 关闭订单 | status ∈ {CANCELLED, COMPLETED} 后系统收敛 |

前端用统一的 `canOrderAction(order, action)` 纯函数计算可用性，并与后端返回的 `allowed_actions`（若提供）取交集。

### 8.4 中文文案与错误提示

| 原则 | 示例 |
|---|---|
| 说清后果 | “取消后订单不可恢复，已支付金额将在 1–3 个工作日原路退回” |
| 指明动作 | “请先选择仓库”而不是“参数错误” |
| 不泄露实现 | 不展示 stack、SQL、内部字段名 |
| 提供出口 | 错误态提供“重试”“返回列表”“复制 request_id” |
| 统一术语 | 订单状态使用“待付款/待发货/已发货/已完成/已关闭”等中文映射 |
| 无歧义 | “部分发货”而非“发货中”；“退款办理中”而非“处理中” |
