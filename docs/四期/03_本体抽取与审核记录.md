### 6.2 改了什么

| 层 | 改动 |
|---|---|
| 表结构 | `ontology.relation.product_scope varchar(32)` + 索引；DDL 唯一事实源 `db/schema.sql`，迁移 `0012_ontology_relation_product_scope.sql` |
| 数据回填 | `PART_OF` 取产品编码、`COVERED_BY` 取政策 `product_id`、`SYMPTOM_OF`/`REMEDY` 取故障 `product`；`ESCALATES_TO` 保持 NULL（跨产品通用） |
| 抽取规则 | 删除 `TRIGGER_PART_RULES`；抽取出的关系写入 `product_scope` |
| 图遍历 | `ontology.graph(..., product_scope=)` 只走"通用或本产品"的边；API `GET /ontology/graph` 新增同名参数 |
| 归一 | 范围优先级 产品 > 故障 > 部件/配件，命中高层后不再用部件兜底；共用部件唯一归属才收窄 |
| 审核 | 新增实体合并、人工补链、派生规则（通用安全事件不挂部件）；只补审 `DRAFT`，不会把 `DEPRECATED` 重新激活 |
| 治理 | 政策点名的动作落成实体，并建立第一条 `GOVERNED_BY` |

### 6.3 不变量（`tests/test_ontology_integrity.py`）

| 断言 | 挡住什么 |
|---|---|
| 谓词域/值域 | `SYMPTOM_OF` 只能故障→部件，`REMEDY` 只能故障→动作… |
| `product_scope` 必须是已存在产品 | 拼错产品码、指向政策编码 |
| 带范围两跳只到本产品保修 | 跨产品保修推断 |
| 故障关系的 scope 与故障自身产品一致 | 抽取写入错误范围 |
| 通用安全事件不挂部件 | 冒烟/触电/鼓包被归到某部件 |
| 政策引用的动作有 `GOVERNED_BY` | 悬空动作引用 |
| 保修政策指向存在的部件 | 保修矩阵与部件表漂移 |
| 同 kind 展示名唯一 / 别名跨实体唯一 | 归一结果不确定 |
| 跨产品故障不被部件收窄 / 共用部件不收窄 | "电池鼓包""主机"被锁到错误产品 |

## 7 v3：接入 06_保修维修与备件

### 7.1 为什么

06 目录此前在本体里是空白：7 篇文档只有《产品与部件保修矩阵》被保修政策编码间接命中，其余 6 篇 **0 映射**；同时 `GOVERNED_BY` 只有 1 条，动作与政策之间几乎没有治理关系。

这批文档不是故障现象，是**政策与流程条文**，所以不套症状抽取那套规则，单独走"文档 → 政策实体 → 动作"。

### 8.2 09_客服SOP：明确不接入

9 篇 SOP 是"处理顺序与话术护栏"，不是业务对象或业务规则：

- 意图清单已在 `13_结构化规则/intent_taxonomy.yaml`；

再给每篇建一个"政策"实体，只会把本体退化成文档目录，并和代码里的真源形成第二份事实。**结论：09 保持不接入，覆盖率 0 是预期结果**，不是遗漏。

同理暂不建的还有 `BASE`（企业介绍/术语表）、`VALID`（校验报告）这类非业务对象文档。
