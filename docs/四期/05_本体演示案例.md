# 四期本体演示案例

> 目的：用一个真实客服问题，说明"本体到底比纯检索多做了什么"。
> 所有输出都是跑出来的，不是示意；复现命令见第 6 节。

## 1 一句话

**检索只能给你几段文档，本体能给你"这是哪个产品的哪个部件、适用哪条政策"的结论**，并且能把范围收窄，避免拿别家产品的保修回答用户。

## 2 主案例：指纹识别差，还在保修吗

选它的原因：用户**没提产品型号**，只说了症状；型号、部件、保修期限都得靠本体补出来。

### 2.1 四步链路

| 步骤 | 输出 | 说明 |
|---|---|---|
| ① 归一 | `SYM-QL-L3P-02`（故障：指纹识别差） | 口语"指纹识别差"命中症状别名，不需要用户报型号 |
| ② 产品范围 | `QL-L3P` | 症状实体自带 `attrs.product`，直接产出二期可用的过滤键 |
| ③ 图遍历 | `SYMPTOM_OF` → 锁体及电子部件 → `COVERED_BY` → `WARRANTY-QL-L3P-MAIN-24M`（24 个月） | 症状到保修的结论只有图能给 |
| ④ 检索 | top5 全部收敛到 QL-L3P 文档 | 不带过滤时 5 条里有 2 条是通用/别的产品 |

### 2.2 图遍历实跑

```
问题：指纹识别差，还在保修吗
① 归一： [('SYM-QL-L3P-02', 'fault', '指纹识别差')]
   产品范围： QL-L3P

② 关系（以 SYM-QL-L3P-02 为起点）：
  图遍历（scope=QL-L3P，depth=2）：
    -SYMPTOM_OF-> lock_body_and_electronics（part）锁体及电子部件
    -REMEDY-> action.clean_and_retry（action）清洁/复位后重试
    -REMEDY-> action.collect_evidence（action）收集订单号与现场凭证
    -REMEDY-> action.create_ticket（action）创建技术工单
      -PART_OF-> QL-L3P（product）栖云智能门锁 L3 Pro
      -COVERED_BY-> WARRANTY-QL-L3P-MAIN-24M（policy）QL-L3P · 锁体及电子部件 保修 24 个月
      -SYMPTOM_OF-> SYM-QL-L3P-01（fault）无法开锁
      -SYMPTOM_OF-> SYM-QL-L3P-03（fault）异常开锁记录
```

同一个起点**不限范围**时，还会顺着"清洁/复位"这条共用动作摸到 `SYM-QR-R5M-02`（扫地机器人）；带上 `QL-L3P` 后这条就被挡掉了。这就是 `product_scope` 的实际作用。

### 2.3 真实回答（接 DeepSeek）

> 无法仅凭"指纹识别差"确认是否在保。L3 Pro 锁体及电子部件保修 24 个月，锁芯保修 24 个月，但需查询购买凭证、序列号、维修和检测记录后才能确认资格。
>
> 建议先按故障排查：清洁指纹识别区、保持手指干燥、重新录入多角度指纹。若持续失败且密码/门卡/钥匙等其他凭证正常，可创建技术工单检测。
>
> 请提供购买时间、序列号，我来帮你进一步核对保修；如涉及未知管理员、陌生登录或异常开锁记录，属于账户安全问题，需按账户安全升级处理，不走普通指纹故障流程。

"24 个月"不是模型猜的，是从 `WARRANTY-QL-L3P-MAIN-24M` 的正文与手册里取到的；"不能仅凭描述认定"来自保修政策实体与 `03` 里的审核结论。

### 2.4 如果没有本体

- 只能靠 BM25/向量命中"指纹""保修"，拿回`配件购买与保修``保修、维修与备件全流程手册`这类通用文档；
- "锁体 24 个月"需要模型自己从表格里读，读错或读漏没有约束；
- 也拿不到 `product_scope` 这个过滤键，检索结果会混入非本产品文档。

## 3 陪衬案例一：电池鼓包了怎么办

**本体在这里的作用是"拦住不该说的话"**：鼓包是跨产品的安全事件，`product_scope` 为 NULL，图里只有 `ESCALATES_TO`，没有 `SYMPTOM_OF`。

```
① 归一： [('battery_swelling', 'fault', '鼓包'), ('battery', 'part', '电池')]
   产品范围： 不收窄
② 图遍历：
    -ESCALATES_TO-> ESC-P1-DEVICE-THERMAL（policy）P1 升级：发热/焦味/鼓包
```

真实回答的要点是"立即停用、不要拆、升级热异常流程"，**全程不谈保修**。

反例（v2 之前的本体）：`battery_swelling` →`SYMPTOM_OF`→ `battery` →`COVERED_BY`→ `WARRANTY-QR-R5M-BATTERY-12M`，门锁用户问鼓包会被报"扫地机电池保修 12 个月"。

## 4 陪衬案例二：主机坏了保修多久

`main_unit` 同时属于 QC-C2G 与 QH-G1，本体**拒绝二选一**：

```
① 归一： [('main_unit', 'part', '主机')]
   产品范围： 不收窄
② 图遍历：
    -PART_OF-> QC-C2G（product）栖云摄像头 C2 守望版
    -PART_OF-> QH-G1（product）栖云家庭网关 Hub G1
    -COVERED_BY-> WARRANTY-QC-C2G-MAIN-12M（12 个月）
    -COVERED_BY-> WARRANTY-QH-G1-MAIN-12M（12 个月）
```

正确行为是反问"是摄像头还是网关"，而不是随便挑一张保修单。这正是 v2 修掉的 bug：之前会取"其中一个"产品范围，把召回锁死。

## 5 一张总表

| 问题 | 归一结果 | 产品范围 | 图的结论 | 期望行为 |
|---|---|---|---|---|
| 指纹识别差，还在保修吗 | 症状 `SYM-QL-L3P-02` | `QL-L3P` | 锁体 → 保修 24 个月 | 报期限 + 要求核验 + 给排查步骤 |
| 电池鼓包了怎么办 | 安全事件 `battery_swelling` | 不收窄 | 仅 `ESCALATES_TO` | 安全处置 + 升级，不谈保修 |
| 主机坏了保修多久 | 部件 `main_unit` | 不收窄 | 两张不同产品的保修 | 反问产品，不猜 |

同一套模型，三种行为：**能定位就定位，不能定位就承认，涉及安全就转轨**。

## 6 复现

```bash
python scripts/ontology_demo.py "指纹识别差，还在保修吗"
python scripts/ontology_demo.py "电池鼓包了怎么办" --top-k 3
python scripts/ontology_demo.py "主机坏了保修多久" --top-k 3
```

`scripts/ontology_demo.py` 只跑确定性部分（归一 → 图 → 带范围检索），不调大模型；上面的回答文字是接 DeepSeek 实跑的，重新生成需要 `LLM_API_KEY`。

## 7 讲解口径（对业务方三句话）

1. 用户说症状、不说型号，我们也能定位到"哪个产品的哪个部件"。
2. 定位之后能直接给出适用政策，并且只拿本产品的文档回答，不串台。
3. 定位不了或者涉及安全，系统会承认并转轨，而不是硬编一个答案。

## 8 演示中发现并修掉的问题

第一次实跑时，安全案例的回答里直接出现了内部编号 `ESC-P1-DEVICE-THERMAL` 和 `ESC-P0-ELECTRICAL`——模型把检索到的升级矩阵原文抄给了用户。已在 `finalize` 的 system prompt 里加了"不向用户展示内部规则编号，用业务说法指代"，复跑确认回答里不再出现编号。

这类问题纯检索看不出来，是拿着真实问题跑一遍才暴露的，建议后续把"回答中不得出现内部编码"加成 eval 断言。
