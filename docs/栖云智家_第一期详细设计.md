### 1.2 关键决策与被否决方案

| 决策 | 采用 | 否决 | 理由 |
|---|---|---|---|
| 前端框架 | React 18 + Ant Design 5 | Vue 3 + Element Plus | 本期后台以高密度表格、复杂表单、批量操作与报表为主；Ant Design 的表格/表单能力与 AntV 可视化生态更完整 |
| 数据库拆分 | 单库多 schema（shared/commerce/knowledge） | 一期即拆多库 | 单库可保证订单与库存的强一致事务；schema 隔离清晰，未来拆库按 schema 迁移成本可控 |
| 库存扣减 | 下单锁库存（available 转 reserved），发货出库 | 下单直接扣减 | 未支付订单不应减少在库总量；分阶段记账便于对账与超时释放 |
| 状态表达 | text + 命名 CHECK 约束 | 原生 ENUM | 状态会随业务增加，原生 ENUM 变更需 ALTER TYPE；CHECK 替换更平滑且报错友好 |
| 鉴权 | JWT access(15 分钟) + 旋转 refresh token（库内哈希） | 长期 JWT | 支持登出、设备管理与泄露吊销 |
| 异步任务 | 一期：数据库任务 + APScheduler + Redis 选主 | 一期即引入 Celery | 一期任务量小（关单、释放预占、导出），避免过早引入 broker 运维成本 |
| 事件 | 事务内写 shared.outbox_event | 直接调用下游 | 避免双写不一致；下游只需消费 outbox |

### 2.4 请求链路与中间件顺序

1. request_id 注入（缺省生成 UUID，回写响应头 X-Request-Id）
2. 结构化日志与耗时（path、method、status、user_id、channel_account_id、duration_ms）
3. CORS（仅允许前端域名）
4. 认证（解析 Bearer，加载用户与角色，校验状态与锁定）
5. 权限（permission code 校验）
6. 渠道范围（channel_account_id 是否在可见集合内）
7. 幂等（写方法要求 Idempotency-Key，命中则回放）
8. 业务处理（服务层开启事务）
9. 审计与 outbox（与业务写同一事务）
10. 统一异常映射（业务错误码转 HTTP + ApiError）

### 2.5 事务与一致性策略

| 场景 | 策略 |
|---|---|
| 下单 | 单事务内：校验、锁库存（条件 UPDATE）、写订单与订单项、写预占、写流水、写 outbox |
| 支付回调 | 单事务内：回调日志去重、支付单幂等更新（PENDING 转 SUCCESS）、订单状态推进、outbox；重复回调直接返回成功 |
| 发货 | 单事务内：写包裹与包裹项、更新订单项已发数量、扣减 reserved、写流水、推进履约状态 |
| 退款 | 先落 refund(PENDING)，调渠道后写 SUCCESS 与订单退款金额；TIMEOUT/UNCERTAIN 保留待核查，禁止自动重试 |
| 跨系统 | 一律 outbox + 幂等键；禁止在事务内做远程调用 |
| 锁顺序 | 多 SKU 下单按 sku_id 升序加锁，避免死锁 |
| 隔离级别 | READ COMMITTED（默认）+ 库存行级条件更新；报表查询使用只读事务 |
| 乐观锁 | inventory.version、orders.version、sku.version 用于后台表单并发编辑 |

### 3.4 状态机

#### 3.4.1 订单业务状态 orders.status

| 当前 | 事件 | 下一 | 触发方 | 副作用 |
|---|---|---|---|---|
| （无） | 创建订单 | CREATED | 客户 | 生成订单号、锁库存、写预占与流水 |
| CREATED | 进入支付 | PENDING_PAYMENT | 系统 | 生成支付单、设置 pay_deadline |
| PENDING_PAYMENT | 支付成功 | PAID | 支付回调 | 更新 paid_amount、paid_at |
| PENDING_PAYMENT/CREATED | 超时或客户取消 | CANCELLED | 系统/客户 | 释放预占、关闭支付单、写流水 |
| PAID | 首次发货 | SHIPPED | 运营 | 扣减 reserved、出库流水 |
| PAID | 全部退款或人工关闭 | CLOSED | 运营 | 必须已有退款或人工审批 |
| SHIPPED | 客户签收 | COMPLETED | 客户/系统 | 写 completed_at，进入售后窗口 |

禁止：从 COMPLETED/CANCELLED/CLOSED 再回到任何进行中状态；PAID 之后不允许直接改价。

#### 3.4.2 支付状态 orders.payment_status 与 payment.status

| orders.payment_status | 触发 | 说明 |
|---|---|---|
| UNPAID | 初始 | 无成功支付 |
| PARTIAL | 部分支付 | 团购/定金场景预留 |
| PAID | 支付成功 | paid_amount 等于 payable_amount |
| REFUNDING | 退款中 | 存在 PENDING/PROCESSING 退款 |
| PARTIAL_REFUNDED | 部分退款完成 | 存在成功退款且小于已支付 |
| REFUNDED | 全额退款完成 | refunded_amount 等于 paid_amount |

payment.status 转移：PENDING 转 SUCCESS（回调验签成功且金额一致）、PENDING 转 CLOSED（超时或订单取消）、PENDING 转 FAILED（渠道明确失败）。仅 PENDING 可被回调推进，保证回调幂等。

#### 3.4.3 履约状态 orders.fulfillment_status

UNSHIPPED 转 PARTIAL_SHIPPED（存在未发完的订单行）转 SHIPPED（全部发出）转 DELIVERED（全部签收）。已发货订单不允许再修改收货地址。

#### 3.4.4 售后状态 after_sales_application.status

| 阶段 | 状态 | 说明 |
|---|---|---|
| 提交 | SUBMITTED | 客户提交，附凭证 |
| 审核 | REVIEWING 转 APPROVED 或 REJECTED | 必须记录 reviewer、reviewed_at、approved_amount |
| 退货 | APPROVED 转 WAITING_RETURN 转 RETURN_SHIPPED 转 RECEIVED | 仅 need_return 为真时进入 |
| 退款 | RECEIVED 或 APPROVED 转 REFUNDING 转 COMPLETED | 触发 refund 记录 |
| 终止 | CANCELLED | 客户撤回或超时未寄回，需写原因 |

orders.after_sales_status 与 order_item.after_sales_status 跟随售后单推进：NONE、APPLYING、PROCESSING、COMPLETED、REJECTED。

### 3.5 库存模型与记账规则

三条数量线：qty_available（可售，未锁定）、qty_reserved（已锁定未出库）、qty_in_transit（在途）。在库总量等于 available + reserved。

| 业务动作 | change_type | qty_delta（在库总量） | available | reserved | 说明 |
|---|---|---:|---|---|---|
| 采购入库 | PURCHASE_IN | +n | +n | 0 | 必须 non-zero 变动 |
| 下单锁定 | RESERVE | 0 | -n | +n | 允许 0 变动（仅改变锁定归属） |
| 取消/超时释放 | RELEASE | 0 | +n | -n | 允许 0 变动 |
| 发货出库 | SALE_OUT | -n | 0 | -n | 实物离开仓库 |
| 退货入库 | RETURN_IN | +n | +n | 0 | 售后收货后 |
| 人工调整 | ADJUST | 正负 | 正负 | 0 | 必填原因，写审计 |
| 报损 | DAMAGE | -n | -n | 0 | 必填原因与凭证 |
| 调拨 | TRANSFER_OUT/TRANSFER_IN | 负/正 | 同步 | 0 | 成对出现 |

记账不变量（已在自检脚本中验证）：
1. inventory.qty_reserved 等于该 SKU×仓库所有 ACTIVE 预占数量之和；
2. 最新一条流水的 qty_after 等于当前 available + reserved；
3. 任何时刻 available 与 reserved 均不小于 0。

### 3.6 防超卖与并发控制

下单锁库存使用条件更新，不依赖应用层读值：

| 步骤 | SQL 语义 |
|---|---|
| 1 | UPDATE commerce.inventory SET qty_available = qty_available - n, qty_reserved = qty_reserved + n, version = version + 1 WHERE sku_id = :sku AND warehouse_id = :wh AND qty_available >= n |
| 2 | 若影响行数为 0，则返回 409 INVENTORY_INSUFFICIENT，整单失败并释放已锁行 |
| 3 | 多 SKU 按 sku_id 升序执行，避免交叉死锁 |
| 4 | 发货出库用 WHERE qty_reserved >= n 保证不超发 |

自检脚本实测结果：锁库存影响行数等于 1、重复支付回调影响行数等于 0、发货出库影响行数等于 1，端到端账实一致判定为真。

### 3.7 幂等、去重与回调安全

| 场景 | 机制 |
|---|---|
| 客户端重复提交下单/取消/退款/库存调整 | shared.idempotency_record 唯一约束 (tenant_id, idem_key)，同 key 同指纹回放原响应，指纹不同返回 409 IDEMPOTENCY_CONFLICT |
| 支付回调重复 | payment_callback_log 唯一 (method, event_id) + payment 更新带 status = PENDING 条件 |
| 物流轨迹重复 | tracking_event 唯一 (shipment_id, event_time, description) |
| 退款重复执行 | refund 状态机 + refund_attempt 唯一 (refund_id, attempt_no) |
| 退款结果不确定 | 记录 UNCERTAIN 并进入人工核查队列，禁止自动重试 |
| 供应商写接口超时 | 统一封装：超时不当失败，先按幂等键或查询接口确认结果 |

### 3.9 迁移策略

1. 所有结构变更只通过 Alembic 迁移，禁止手工改生产库。
2. 迁移命名 revision 加序号加动词，如 0003_add_order_after_sales_status。
3. 每个迁移必须实现 downgrade；不可逆迁移需在文件中显式声明并写明原因。
4. 大表加列使用可空或带默认值，索引使用 CONCURRENTLY（Alembic 中以 autocommit 块执行）。
5. 上线顺序：先加字段与索引，再发布兼容代码，最后清理旧字段与新代码切换。
6. 每次上线前对 schema 与模型做一致性校验（alembic check 或元数据对比脚本）。

### 4.4 关键接口示例

创建订单 POST /orders（Idempotency-Key: 3f1c...）：

请求要点：channel_account_id、address_id 或地址快照、items[{sku_id, quantity}]、buyer_remark、client_time。

响应要点：order_no、status、payment_status、payable_amount、pay_deadline、items、payment{payment_no, method, pay_url}、reservations[]。

支付回调 POST /webhooks/payment/{channel}：

请求要点：event_id、payment_no、amount、currency、channel_txn_no、paid_at、signature。

处理规则：验签失败返回 401 SIGNATURE_INVALID；event_id 已处理直接返回 200；payment 非 PENDING 返回 200 且不重复记账；金额不一致返回 422 并告警。

发货 POST /orders/{id}/ship：

请求要点：warehouse_id、carrier_id、tracking_no、items[{order_item_id, quantity}]、package_count。部分发货时订单进入 PARTIAL_SHIPPED，未发数量保留。

售后审核 POST /after-sales/applications/{id}/review：

请求要点：decision（APPROVE 或 REJECT）、approved_amount、need_return、review_note、sla 变更。通过后进入 APPROVED 或 WAITING_RETURN。

退款执行 POST /refunds/{id}/execute：

请求要点：amount、method、idempotency_key、reason。成功返回 SUCCESS 与 channel_refund_no；超时返回 202 REFUND_RESULT_UNCERTAIN 并进入核查队列。

库存调整 POST /inventory/adjust：

请求要点：sku_id、warehouse_id、change_type（ADJUST、DAMAGE、PURCHASE_IN）、qty_delta、reason、version。返回调整后 available、reserved、流水 id。

订单时间线 GET /orders/{id}/timeline：

返回按时间升序的 field、from_value、to_value、reason、operator_type、created_at，供前端时间线组件直接渲染。

### 4.5 Webhook 规范

| 项 | 约定 |
|---|---|
| 签名 | HMAC-SHA256（时间戳 + 原始报文），密钥按渠道配置在密钥管理服务，不入库明文 |
| 时间窗 | 请求时间戳与服务器相差超过 5 分钟判定过期 |
| 去重 | 以渠道 event_id 落 payment_callback_log，唯一约束兜底 |
| 重试 | 渠道重试一律返回 200 表示已接收；处理失败记录并进入补偿任务，不让渠道无限重试 |
| 幂等 | 业务更新全部带状态条件，重复回调不改数据 |
| 可观测 | 回调原始报文、验签结果、处理结果、耗时入日志与表 |

## 5 关键业务流程

### 5.1 下单

~~~mermaid
sequenceDiagram
  participant C as 客户端
  participant A as API
  participant S as 订单服务
  participant I as 库存服务
  participant D as PostgreSQL
  C->>A: POST /orders (Idempotency-Key)
  A->>A: 鉴权、权限、渠道范围、幂等检查
  A->>S: 创建订单用例
  S->>D: 校验 SKU 与价格、地址
  S->>I: 按 sku_id 升序锁库存
  I->>D: 条件 UPDATE inventory + 流水 + 预占
  S->>D: 写 orders、order_item、order_status_history
  S->>D: 写 outbox_event(order.created)
  S->>D: 写幂等记录并提交
  A-->>C: 订单号、支付单、支付截止时间
~~~

| 步骤 | 校验与处理 | 失败结果 |
|---|---|---|
| 1 | 身份、权限、渠道可见性、幂等键 | 401、403、409 IDEMPOTENCY_CONFLICT |
| 2 | SKU 状态 ON_SALE、商品上架、渠道可售 | 422 VALIDATION_FAILED 或 409 SKU_UNAVAILABLE |
| 3 | 数量 1 到 999、库存充足、地址属于本人 | 409 INVENTORY_INSUFFICIENT、403 |
| 4 | 金额计算：goods、discount、shipping、payable | 校验公式，落库前后一致 |
| 5 | 写单、写预占、写流水、写事件 | 任一失败整单回滚 |
| 6 | 生成支付单与 pay_deadline（默认 30 分钟） | 支付单失败不影响订单创建，可重试发起 |

### 5.2 支付与回调

| 步骤 | 处理 |
|---|---|
| 1 | 支付网关返回 event_id、payment_no、amount、signature |
| 2 | 验签失败返回 401 并记录，人工告警 |
| 3 | 时间戳超窗返回 401 并记录 |
| 4 | payment_callback_log 插入，唯一冲突说明重复，直接返回 200 |
| 5 | 金额与币种与支付单比对，不一致返回 422 并告警 |
| 6 | 条件更新 payment：status 由 PENDING 转 SUCCESS，写 channel_txn_no 与 paid_at |
| 7 | 更新订单 paid_amount、paid_at、payment_status 与 status |
| 8 | 写 outbox_event(payment.succeeded)，写审计 |
| 9 | 返回 200，渠道不再重试 |

支付超时：调度器每分钟扫描 pay_deadline 已过且状态为 CREATED 或 PENDING_PAYMENT 的订单，关闭支付单（PENDING 转 CLOSED）、订单转 CANCELLED、释放预占、写流水与事件。

### 5.3 超时关单与预占释放（任务）

| 任务 | 频率 | 处理 | 幂等保证 |
|---|---|---|---|
| close_order | 每分钟 | 找超时未支付订单，关单并释放库存 | 订单状态条件更新 + 幂等键 |
| release_reservation | 每分钟 | 释放过期且未消费的预占 | 预占状态条件更新为 EXPIRED |
| export_report | 按需 | 生成报表文件写入对象存储 | 任务表唯一键 |
| callback_replay | 每 5 分钟 | 重放未完成回调（仅只读确认，不重复写） | event_id 去重 |

### 5.4 发货与部分发货

| 步骤 | 处理 |
|---|---|
| 1 | 权限 shop:fulfillment:write，订单必须为 PAID 或 PARTIAL_SHIPPED |
| 2 | 校验发货数量不超过订单行未发数量 |
| 3 | 写 shipment 与 shipment_item，运单号在承运商维度唯一 |
| 4 | 扣减 reserved（WHERE qty_reserved >= n），写 SALE_OUT 流水 |
| 5 | 更新 order_item.shipped_quantity |
| 6 | 全部发完则 fulfillment_status 转 SHIPPED、status 转 SHIPPED；否则 PARTIAL_SHIPPED |
| 7 | 写审计与 outbox_event(shipment.created) |
| 8 | 通知客户（本期为站内记录，短信/邮件适配器预留） |

物流轨迹：承运商回调或人工补录写入 tracking_event，唯一约束去重；签收事件到达且全部包裹签收时，订单进入 COMPLETED。

### 5.5 取消订单

| 场景 | 处理 |
|---|---|
| 未支付 | 订单转 CANCELLED，释放预占与库存，关闭支付单 |
| 已支付未发货 | 生成 after_sales_application(REFUND_ONLY) 与 refund(PENDING)，审核通过后执行退款；订单在退款完成后转 CLOSED |
| 已发货 | 不允许直接取消，引导走退货退款售后流程 |
| 并发取消 | 订单状态条件更新，重复请求按幂等键回放 |

### 5.6 售后退款全链路

| 阶段 | 责任方 | 数据变化 |
|---|---|---|
| 提交 | 客户 | after_sales_application(SUBMITTED) 与明细、凭证；订单 after_sales_status 转 APPLYING |
| 审核 | 售后专员 | REVIEWING 转 APPROVED 或 REJECTED，写 reviewer、approved_amount、sla |
| 寄回 | 客户 | WAITING_RETURN 转 RETURN_SHIPPED，写承运商与运单号 |
| 收货 | 售后专员 | 转 RECEIVED，可触发入库流水 RETURN_IN |
| 退款 | 系统与售后 | refund(PENDING) 转 PROCESSING 转 SUCCESS，写 refund_attempt，更新订单 refunded_amount 与 payment_status |
| 完成 | 系统 | 售后转 COMPLETED，订单 after_sales_status 转 COMPLETED |
| 不确定 | 人工 | refund_attempt 记为 UNCERTAIN，进入核查队列，禁止自动重试 |

退款金额约束：单笔退款不超过订单行可退金额；订单累计退款不超过已支付金额（数据库 CHECK 约束兜底）。

### 5.7 库存调整

管理员通过 POST /inventory/adjust 提交：SKU、仓库、变动类型、变动数量、原因、version。服务端校验权限、锁行、比对 version、更新数量、写流水与审计。低于安全库存时进入预警视图与看板提醒。

### 5.8 报表统计口径

| 指标 | 口径 |
|---|---|
| 订单数 | 排除 CANCELLED 的订单数 |
| 支付订单数 | payment_status 属 PAID、PARTIAL_REFUNDED、REFUNDED |
| 应付金额 | 订单 payable_amount 之和 |
| 实收金额 | paid_amount 之和 |
| 退款金额 | refunded_amount 之和 |
| 净收入 | 实收金额减退款金额 |
| 履约及时率 | shipped_at 减 paid_at 在承诺时效内的比例 |
| 售后超时率 | sla_due_at 已过且未完结的售后单占比 |
| 库存可售 | qty_available 减 qty_reserved（视图 sellable_qty） |

统计时区以企业运营时区（Asia/Shanghai）为准，视图按自然日分组。

### 8.2 安全设计

| 领域 | 措施 |
|---|---|
| 口令 | bcrypt（pgcrypto 或 Python bcrypt），禁止明文与可逆加密；改密吊销全部会话 |
| 令牌 | 短期访问令牌 + 旋转刷新令牌；刷新令牌只存哈希，支持按族吊销 |
| 越权 | 每个端点校验权限码与资源归属；后台列表强制叠加渠道范围 |
| 注入 | 全量参数化查询；排序与过滤字段白名单 |
| 上传 | 扩展名、MIME、文件头三方校验，大小与数量限制，校验和去重，存储隔离 |
| 敏感信息 | 不采集支付要素；手机号与地址按角色脱敏展示；日志与埋点禁止记录令牌与完整联系方式 |
| 审计 | 所有写操作记录 actor、action、resource、before/after、request_id、ip、ua |
| 回调 | HMAC 签名 + 时间窗 + event_id 去重 |
| 传输 | 生产强制 HTTPS 与 HSTS，CORS 仅允许前端域名 |
| 密钥 | 全部走环境变量或密钥管理，仓库只提交 .env.example |

### 12.3 环境变量清单（示例，值不入库）

| 变量 | 说明 |
|---|---|
| APP_ENV | dev、test、staging、prod |
| DATABASE_URL | postgresql+psycopg://用户:口令@主机:端口/库名 |
| REDIS_URL | 可选，缺省降级为内存实现 |

### 12.4 命令速查

| 目的 | 命令 |
|---|---|
| 重建本地库 | docker exec ai_customer_service-postgres-1 psql -U ai_customer_service -d postgres -c "DROP DATABASE IF EXISTS qiyun_shop_dev;" -c "CREATE DATABASE qiyun_shop_dev OWNER ai_customer_service;" |
| 应用 DDL | docker cp output/phase1/schema.sql ai_customer_service-postgres-1:/tmp/phase1_schema.sql && docker exec ai_customer_service-postgres-1 psql -U ai_customer_service -d qiyun_shop_dev -f /tmp/phase1_schema.sql |
| 导入种子 | docker cp output/phase1/seed_all.sql ai_customer_service-postgres-1:/tmp/phase1_seed.sql && docker exec ai_customer_service-postgres-1 psql -U ai_customer_service -d qiyun_shop_dev -f /tmp/phase1_seed.sql |
| 自检 | docker cp output/phase1/verify_phase1.sql ai_customer_service-postgres-1:/tmp/verify_phase1.sql && docker exec ai_customer_service-postgres-1 psql -U ai_customer_service -d qiyun_shop_dev -f /tmp/verify_phase1.sql |
